- **可读性**：使用业务名称、明确单位，复杂算法说明公式和假设；不吞异常，不把未知/失败当有效零值。新增或重构按 `AI_CODE_GENERATION.md` 自查，不添加无用抽象层。规范来源按需查看 `CODING_STANDARDS_CATALOG.md`。

- **落实方式**：新独立应用将适用规则复制到项目 docs，由项目 AGENTS.md 引用；构建不依赖本机全局规则路径。修改旧工程仅处理任务涉及部分，验证如实报告，不宣称未执行的格式/静态检查已通过。

# 分语言代码格式规则

版本 1.0。这里只规定命名、缩进、换行、空格、注释和文件排版，不扩展架构或业务要求。这是项目选择的统一风格，不宣称逐条等同于阿里、微软或其他厂家的原文。

已有文件保持一致；公开接口、C ABI、配置键、数据库字段不因格式要求改名。新模块采用本表；格式化仅处理自有源代码，不处理第三方、生成文件和发布产物。语言版本保持原工程设置。

## 1. 所有语言通用

- UTF-8 编码；新文件默认 LF 换行，现有工程有明确要求时沿用。Windows 批处理 `.cmd/.bat` 用 CRLF。
- 每级缩进 4 个空格，不用 Tab；JSON、YAML、HTML、CSS、XML/XAML 用 2 个空格。Makefile 的命令缩进必须用 Tab，是例外。
- 一行一条语句；运算符两侧加空格，逗号后加空格；行尾不留空格，文件末尾保留一个换行。
- 新工程每行建议不超过 120 字符；方法间空一行，最多一行连续空行。长 URL、字符串等不为了限长改变内容。
- 不挤成单行分支；有大括号的语言，`if/else/for/while` 即使单条语句也写完整括号。
- 长参数列表按参数换行，每个参数一行；调用、运算和布尔表达式在自然边界换行，不压缩代码。
- 标识符用明确英文，不用拼音、随意缩写和 `data1/data2`；局部循环索引 `i/j` 可用。测量量值用 `Mm`、`Cm3`、`Px`、`Percent` 或对应蛇形后缀标明单位。
- 注释优先使用清楚的中文，保留必要英文术语；说明用途、单位和复杂部分的原因，不逐行翻译语句。

- 所有具名方法（含私有方法、构造函数、事件及局部函数）须有用途说明；复杂方法体说明关键步骤、约束与原因。各语言格式、例外与检查口径见 [方法与方法体注释](rules/METHOD_COMMENTS.md)。

## 3. C++（现有算法使用 C++17）

- 头文件 `.h/.hpp`，实现文件 `.cpp`；文件名沿用工程的小写下划线风格，如 `volume_calculator.cpp`。
- 大括号采用 Allman 风格；`else` 独立一行。命名空间内也缩进 4 空格，访问修饰符与类左括号对齐。
- 指针/引用符号贴类型：`const Frame& frame`、`const float* depthMm`；每行只声明一个变量。
- `#include` 按本模块头文件、项目头文件、第三方头文件、标准库分组，组间空一行；既有顺序不自动调整。
- 公共接口用 `/** ... */`，适用时写 `@brief`、`@param`、`@return`；函数内用 `//`。

```cpp
/**
 * @brief 根据净尺寸计算矩形箱格容量。
 * @param lengthMm 内部净长，单位 mm。
 * @param widthMm 内部净宽，单位 mm。
 * @param heightMm 内部净高，单位 mm。
 * @return 容量，单位 cm³。调用方保证尺寸有效且为正。
 */
double calculateCapacityCm3(double lengthMm, double widthMm, double heightMm)
{
    constexpr double kCubicMillimetersPerCubicCentimeter = 1000.0;
    return lengthMm * widthMm * heightMm / kCubicMillimetersPerCubicCentimeter;
}
```

## 4. C#（现有容积应用保持 C# 5）

- 文件名与主要类型一致，如 `VolumeCalculator.cs`；类型、方法、属性 PascalCase，接口加 `I`。
- Allman 大括号；`using` 放在命名空间外，`System` 组在前，项目组在后；组间空一行。
- 顺序建议为字段、构造函数、属性/事件、公共方法、私有方法；相关成员靠近，不无故大范围重排旧类。
- 公共 API 使用 `///` XML 注释；复杂实现用 `//`。字符串使用双引号。
- 保留普通块形式 `namespace`、`using (...) { ... }`；格式示例不引入 C# 5 不支持的新语法。

```csharp
/// <summary>计算载货率，单位 %。</summary>
/// <param name="cargoVolumeCm3">货物体积，单位 cm³。</param>
/// <param name="capacityCm3">容量，单位 cm³，必须大于零。</param>
/// <returns>载货率，单位 %。</returns>
public double CalculateLoadPercent(double cargoVolumeCm3, double capacityCm3)
{
    if (capacityCm3 <= 0)
    {
        throw new ArgumentOutOfRangeException("capacityCm3");
    }

    return cargoVolumeCm3 / capacityCm3 * 100.0;
}
```

## 5. Java

- 文件名与公开类一致，如 `VolumeCalculator.java`；包名全小写，方法/变量 lowerCamelCase。
- 起始大括号同行；写成 `} else {`、`} catch (...) {`；控制关键字与左括号之间留空格，方法名与左括号之间不留空格。
- 常量大写下划线，字符串双引号；注释采用 Javadoc。导入按项目分组，不为格式化擅自改变依赖。

```java
/**
 * 计算载货率。
 * @param cargoVolumeCm3 货物体积，单位 cm³
 * @param capacityCm3 容量，单位 cm³，必须大于零
 * @return 载货率，单位 %
 */
public double calculateLoadPercent(double cargoVolumeCm3, double capacityCm3) {
    if (capacityCm3 <= 0) {
        throw new IllegalArgumentException("capacityCm3 must be positive");
    }

    return cargoVolumeCm3 / capacityCm3 * 100.0;
}
```

## 6. TypeScript / JavaScript / React

- 4 空格；起始大括号同行；语句分号保留；普通字符串单引号，JSX 属性双引号。
- 多行对象、数组和参数列表保留格式化器支持的尾逗号；箭头函数参数保留括号。
- 类型、接口、React 组件 PascalCase；函数和变量 camelCase；组件文件使用 `VolumePanel.tsx`，普通模块跟随既有目录风格。
- 导出接口用 JSDoc/TSDoc。方法间空一行；短对象可以同行，禁止手工对齐多列空格。
- Forge IDE 当前 `.prettierrc.json` 的 110 字符行宽继续有效；120 为新工程默认值。

```typescript
/** 计算载货率（%）；两个输入均使用 cm³，容量须大于零。 */
export function calculateLoadPercent(cargoVolumeCm3: number, capacityCm3: number): number {
    if (capacityCm3 <= 0) {
        throw new RangeError('capacityCm3 must be positive');
    }

    return (cargoVolumeCm3 / capacityCm3) * 100;
}
```

## 7. Python 与 PowerShell 工具脚本

Python：类 PascalCase、函数/变量 snake_case、常量全大写；顶层函数/类之间空两行，类内方法间空一行，这是通用空行规则的例外。注释用 `#`，接口说明用三双引号 docstring；普通字符串统一双引号，不写行尾分号。

```python
def calculate_load_percent(cargo_volume_cm3, capacity_cm3):
    """计算载货率（%）；输入为 cm³，容量必须大于零。"""
    if capacity_cm3 <= 0:
        raise ValueError("capacity_cm3 must be positive")

    return cargo_volume_cm3 / capacity_cm3 * 100.0
```

PowerShell：函数用标准动词加业务名，例如 `Get-CellVolume`；公开参数用 PascalCase、局部变量 camelCase；起始括号同行，运算符两侧空格。字面字符串单引号，需要变量插值时双引号；公共脚本用 `<# .SYNOPSIS / .PARAMETER / .EXAMPLE #>` 注释帮助。禁止复用 `$HOME` 等系统变量作为业务变量。

## 8. 配置与标记文件

- JSON：2 空格、双引号、无注释、无尾逗号；配置键保持已有协议，不因命名风格改变键名。
- YAML：2 空格，不使用 Tab，列表项用 `- `。
- HTML/XML/XAML：2 空格，属性值双引号；多属性长行拆行并统一缩进。
- CSS：2 空格，每个属性一行，冒号后一个空格，分号结尾；选择器及类名延续原工程。
- Markdown：标题/段落/列表间空一行，代码块标明语言，列表不手工用空格排表。

## 9. 编辑器配置模板

配置模板放在 [code-format](rules/code-format/) 目录，可复制到新应用根目录。现有配置先合并差异，不直接覆盖；本次未对现有源代码运行批量格式化。

| 文件 | 管理范围 | 不负责 |
| --- | --- | --- |
| `.editorconfig` | 编码、缩进、行尾；支持相应属性的 C# 编辑器还可提示命名/括号 | 不保证所有编辑器支持扩展规则，不校验业务 |
| `.clang-format` | C++ 空格、大括号、换行、缩进 | 不自动重命名，不保证插入缺少的分支括号 |

示例用于展示格式，不是完整数值校验实现，不应替换项目已有算法。需要修改旧代码时单独做格式变更，不夹带公式、阈值或接口调整。

# 方法与方法体注释规则

2026-11-05：用户补充的全局编码要求。适用于自有代码的新建、生成和修改；不宣称属于阿里巴巴等厂商的原文。保留语言版本、接口和现有行为。

## 必须写在哪里

- 所有具名函数、方法、构造函数、事件处理、局部辅助函数都要有紧邻声明的用途说明，不限 public；private/internal 同样适用。
- 方法前说明“做什么、为何存在”，按实际需要补充参数含义、单位、返回值、失败语义、副作用和资源/线程约束。简单方法可用一句准确说明，不机械填写空标签。
- 方法体内对非直观的步骤写注释：输入限制的原因、主要阶段、算法公式与假设、状态切换、并发与取消、回退策略、异常处理、资源释放。注释放在对应代码前，不能只在方法头写一句泛泛描述。
- 复杂事件回调、异步回调即使匿名也应解释关键逻辑；简单 map/filter 比较、直接委托和属性读写不要求逐个附加重复说明，可由所在方法的契约覆盖。
- 接口声明作为调用契约的权威说明；实现可引用该契约，但应补充私有实现的关键步骤。纯框架生成文件不手工修改，从自有生成模板落实。

## 写什么、不写什么

- 默认中文，术语和标识符保留必要英文。说明实际行为及限制，不写“处理数据”“执行方法”“逻辑如下”等空话。
- 不逐行翻译赋值和循环，不为达标插入无意义步骤编号；短且直观的方法无需再在方法体重复方法头。
- 错误可能抛出、返回空值、取消或保留旧数据时必须明确；不能把未知写成零值或把估算写成实测。
- 数值计算写清公式、单位、坐标、阈值来源；持久化写清覆盖/合并策略；事件与并发写清状态归属及释放时机。
- 更新实现时同步更新注释；修复过期注释。注释不能替代缺失功能，也不能为了符合注释偷偷改变行为。

## 各语言形式

| 语言 | 方法说明 | 方法体说明 |
| --- | --- | --- |
| C / C++ | Doxygen `/** ... */`；接口适用时写 `@param`、`@return`、所有权与异常边界 | `//`，说明几何/内存/并发假设 |
| C# / WinForms / WPF | `/// <summary>`；适用时写 `param`、`returns`、`exception`，事件方法也适用 | `//`，说明 UI 线程、取消、资源与绑定关系 |
| Java / Android Java | Javadoc `/** ... */`，适用时写参数、返回值和异常 | `//`，说明生命周期、业务分支和线程 |
| Kotlin / Android Kotlin | KDoc `/** ... */` | `//`，说明协程与生命周期 |
| JS / TS / Vue 脚本 | JSDoc / TSDoc `/** ... */`，组件和具名回调也适用 | `//`，说明状态、异步结果归属和边界 |
| Python | 函数首条语句用三双引号 docstring，适用时列 Args / Returns / Raises | `#`，说明实际模型/计算流程 |
| PowerShell | 函数前或体首用 `<# .SYNOPSIS ... #>`；适用时补充参数与示例 | `#`，说明路径、进程、编码与失败处理 |

HTML/CSS/XAML 没有方法体，说明组件/样式块的用途和特殊约束即可。JSON 不支持注释，将说明放在 schema 或相邻文档。

## 简例（TypeScript）

```typescript
/** 将工程目录册写入磁盘；持锁期间重新读取，避免不同窗口互相覆盖。失败交给调用方显示。 */
async function updateCatalog(change: (projects: Project[]) => void): Promise<void> {
    const lock = await acquireLock();
    try {
        // 获取锁后再读取，不能使用窗口打开时缓存的旧目录册。
        const projects = await readCatalog();
        change(projects);
        // 完整写入临时文件后再替换，避免读到半截 JSON。
        await replaceCatalog(projects);
    } finally {
        // 修改或写入失败也必须释放本次持有的锁。
        await lock.release();
    }
}
```

# 可人工阅读与维护的分语言编码规则

版本 1.0 · 2026-11-05。适用于所有后续工程的新建和修改。目标：维护者能从名称找到功能、从入口看懂流程、修改一个规则时知道影响和验证方式。

本规则参考华为 LiteOS 的组织方式，按“项目 → 文件 → 类型 → 方法 → 变量 → 注释 → 错误”制定本地要求，不冒充任何厂家的完整规范。排版以 CODE_FORMAT.md 为准，方法注释以 METHOD_COMMENTS.md 为准。已有公开接口、配置协议、反射/绑定名称和语言版本不能为改名而破坏。

## 1. 通用强制规则

| 编号 | 对象 | 执行规则与例子 |
| --- | --- | --- |
| READ01 | 项目 | 名称表达业务，README 写明用途、入口、目录职责、依赖、构建、运行和测试命令。应用独立运行，不依赖 IDE 私有路径。 |
| READ02 | 文件/模块 | 按功能命名，例如 camera_session、VolumeCalculator、project-catalog；不出现 Common2、UtilsNew、final_final。已有约定保留，新文件与相邻模块一致。 |
| READ03 | 类/结构/接口 | 名词或名词短语；注释说明职责、持有的状态及重要生命周期。一个类型不混合控件布局、算法、数据库和设备协议。无状态小功能允许普通函数，不强制造类。 |
| READ04 | 方法 | 动词＋业务对象，例如 LoadBoxPreset、calculateCapacityCm3；名称反映读写或副作用。禁止用 Process、Do、Handle1 隐藏实际工作。框架规定的事件/重写名称例外。 |
| READ05 | 方法体 | 主要流程按输入检查、处理、输出排列；用具名中间结果解释复杂判断；不写嵌套三元、布尔参数串或副作用混杂的表达式。 |
| READ06 | 变量 | 使用业务词和单位，例如 frameWidthPx、timeoutMs、loadPercent；用 is/has/can 表达布尔意义。短循环索引 i/j、惯用坐标 x/y/z 可保留，坐标系须明确。 |
| READ07 | 常量/状态 | 阈值具有名称、单位、范围和来源；状态用枚举/明确类型表达。不得把未知、未执行、错误替换为有效零值。 |
| READ08 | 注释 | 所有具名方法（含构造、私有、事件、局部函数）说明用途；复杂步骤解释原因、边界和资源处理。类型说明职责；字段仅在含义、单位、状态归属不明显时补注释。不逐行翻译赋值。 |
| READ09 | 资源/并发 | 明确谁创建、谁释放、何时取消、在哪个线程回调。UI 不同步等待长任务；后台结果校验会话和输入归属。 |
| READ10 | 错误/界面 | 错误状态保留。界面用简短中文说明影响及下一步；内部堆栈、路径细节放日志，禁止自动反复弹整屏技术异常。编译诊断在输出/问题面板保留。 |
| READ11 | 人工修改 | 业务规则集中在相应模块；布局生成和手写事件分开；不依赖神秘数值下标，不用运行时生成代码替代普通可编辑源文件。 |
| READ12 | 兼容重构 | 使用语言重命名能力或逐引用修改，并检查字符串反射、XAML/Vue 绑定、P/Invoke、导出符号、JSON、数据库。名称改善与算法/阈值调整分开提交或明确区分。 |

方法约 60 个有效代码行、文件约 500 行、嵌套超过 3 层时需要检查职责；这是人工审阅信号，不是硬性截断。状态机、生成布局、数据表及有证据的性能热点可保留并解释。禁止为凑行数拆成大量无意义转发函数。

## 2. 按语言执行

### C

- 项目/模块与文件用业务名，小写下划线：camera_session.c/.h；接口头只放必要声明，内部函数用 static 限定范围。
- 新独立 C 模块类型用 PascalCase；普通函数使用模块前缀加明确动作，例如 camera_session_open；参数、字段和局部变量用 lowerCamelCase；宏/枚举常量用 MODULE_UPPER_SNAKE_CASE。既有 tv_* ABI、驱动或华为 LiteOS 模块保留原命名。
- Doxygen 说明缓冲区长度、单位、输出参数、错误码和释放方；一个声明只定义一个变量。输出参数只在成功条件下有效，调用者不得猜测。
- Allman 大括号、4 空格。上述命名为本地选择，不声称与 LiteOS 大驼峰函数规则完全相同。

### C++

- 文件 volume_calculator.cpp/.hpp；类/结构/枚举 VolumeResult；函数 calculateVolume；局部 cellHeightMm；私有字段 cellHeightMm_；常量 kMaxCellCount。遵守已有模块的一致风格。
- 类型注释说明职责；函数 Doxygen 说明所有权、单位、坐标系及失败条件。使用 RAII，默认不写裸 owning 指针，不用宏代替普通函数。
- 传统算法默认放独立 C++ 库；C ABI 不暴露 STL、不让异常跨边界；命名规范不改变 ABI、结构布局或调用约定。

### C# / WinForms / WPF

- 工程/命名空间采用明确业务层级，例如 Tote.Measurement.Core；文件与主要类型一致，如 VolumeCalculator.cs。
- 类型/方法/属性 PascalCase；接口 ICameraSource；参数/局部 camelCase；新模块私有字段 _cameraSession；常量 MaxCellCount。真实异步方法用 Async 后缀，不在同步方法上假加 Async。
- 类型、构造和所有具名方法用 XML summary；必要时 param/returns/exception。控件使用 openCameraButton、resultGrid 等业务名，避免 button1/textBox2；改旧控件时同步 Designer、事件和资源绑定。
- .Designer.cs/.g.cs 与手写事件/应用服务分开；WPF XAML、绑定 ViewModel 和服务分开。生成文件不手工塞入业务逻辑。
- 保留工程目标 C#/.NET 版本；不因示例使用新语法而升级旧 Framework 项目。

### Java / Android Java

- 包名全小写，公开类与文件同名；类 BoxPresetService，方法 loadBoxPreset，局部 presetId，常量 MAX_RETRY_COUNT。
- 类型与全部具名方法使用 Javadoc，说明职责、参数和异常；不要给所有成员机械增加无效 getter/setter。
- UI Activity/Fragment 只做显示和生命周期协调；业务规则不塞进 onCreate/onClick。Android 资源名小写下划线，例如 button_open_camera。
- 阿里 P3C 用于 Java；现有 Android/AOSP 子工程遵守原规定，不跨项目强制改成 AOSP 的 mField 风格。

### Kotlin / Android Kotlin

- 类型/文件 PascalCase，函数与属性 lowerCamelCase，const val 常量 UPPER_SNAKE_CASE；KDoc 描述类型和具名函数。
- 明确 nullable 语义，避免无理由 !!；协程注明所属 scope、取消和线程要求，不把全局协程用于页面生命周期任务。
- Compose 组件按框架惯例 PascalCase；资源和 Gradle 结构保持框架规范，不强行搬进通用 source 目录。

### JavaScript / TypeScript / Node.js

- 类型/组件 PascalCase，函数/变量 camelCase，真正固定常量 UPPER_SNAKE_CASE；组件文件 PascalCase，普通文件沿用模块的 kebab-case 或既有约定。
- 使用 JSDoc/TSDoc；每个具名方法说明用途，复杂异步流程说明取消、过期结果、失败传播；禁止用类型断言代替外部输入校验。
- 一个模块负责一种业务；网络、文件、进程访问封装在适配模块，渲染代码不直接持有系统权限。命令、输入、路径使用结构化参数，不拼接不可信 shell 字符串。
- new 项目采用 strict TS；现有 JS 不为符合规范而自动迁移 TS。4 空格、起始大括号同行，分号保留。

### Vue / HTML / CSS

- Vue 组件使用多词业务名，如 BoxPresetEditor.vue；props 说明类型/含义，事件说明携带数据，复杂计算进入具名函数或 composable。
- 模板只保留展示和简单绑定，不塞算法、复杂三元及长链式表达式；单文件组件不是把所有业务写在一个文件的理由。
- HTML 使用语义标签，CSS 类表达用途，例如 project-list、is-selected；不使用 div1、blueText1 绑定业务。样式令牌集中维护，禁止为格式要求改变已有 class/selector 协议。
- HTML/CSS/XML 用 2 空格；脚本遵循 JS/TS 规则。对组件边界和特殊布局约束写注释，不给每个 div 重复说明。

### Python

- 模块 snake_case.py，类 PascalCase，函数/变量 snake_case，常量 UPPER_SNAKE_CASE；内部约定用单下划线前缀。
- 类及所有具名函数写 docstring；必要时说明 Args、Returns、Raises，算法/模型注明单位、形状、数据类型和设备假设。
- 路径/模型加载/推理与 UI 分离，资源使用 context manager 或 finally。类型提示按工程版本执行。
- Python 的使用范围仍遵守 CPP_PYTHON_RULES.md：直接 AI 模型工作或用户明确指定；不是所有算法默认转 Python。

### JSON / YAML / XML / XAML

- 键名、序列化字段、路由和绑定是契约，不因统一大小写而重命名。
- JSON 不写注释；schema 的 title/description 说明含义、单位、范围，或写相邻配置说明。schema 的 default 不等于运行时自动填充值。
- YAML/XML/XAML 用注释说明复杂配置块与绑定约束。环境路径和凭据不硬编码进通用项目模板。

### PowerShell / Bash / CMD / CMake / SQL

- PowerShell 用批准动词＋业务名，如 Get-ProjectStatus，参数 PascalCase、局部 camelCase；函数写注释帮助，保留实际错误退出码。
- Bash 函数/局部变量 snake_case，常量与导出环境变量 UPPER_SNAKE_CASE；函数前说明输入、输出、副作用及退出码，路径引用加引号。4 空格是本地选择。
- CMD 子程序标签和 CMake 函数写业务名及用途注释；声明输入、输出和工作目录；不使用系统变量名承载业务临时值。
- SQL 表列名沿用数据库契约；新模块用一致 snake_case，查询别名可读，禁止 a1/b2 代表复杂业务。迁移与回滚条件清楚，事务边界有说明。

尚未列出的语言：先查语言官方/维护方规范，再形成项目差异表；继续执行通用规则，不虚构“全部语言已经配置自动检查”。

## 3. 如何改旧工程

1. 先记录该模块入口、调用方、公开接口、持久化字段、构建命令与当前验证基线。
2. 先补准确注释和业务命名；一次只处理一个功能边界。使用符号重命名，禁止全目录字符串替换所有相同短词。
3. 方法过长时按实际步骤拆分，保留处理顺序、线程、异常和资源归属；不擅改算法、标定、容差或用户配置。
4. 运行对应编译、关键回归及适用静态检查；说明改了哪些模块、剩余范围、哪些工具没运行。
5. 第三方、自动生成布局、构建缓存、发布包不做可读性重写。业务代码人工能修改并独立构建是验收重点，不以注释数量代替质量。

## 2. 文件放置规则

| 文件或功能 | 放置位置 | 规则 |
| --- | --- | --- |
| C ABI 声明 | `source/native/include/` | C# 调用边界的原生声明唯一来源；不混入 UI 或厂商私有类型。 |
| C++ 内部实现与头文件 | `source/native/src/` | 内部实现不全部暴露到 include；文件沿用 `volume_calculator.cpp` 风格。 |
| C# 原生调用 | `source/managed/interop/` | DllImport、结构映射集中维护，窗体不散落 DllImport。 |
| 窗体布局 | `ui/MainForm.Designer.cs` | 仅布局和控件初始化；生成器只覆盖明确归属的布局文件。 |
| 窗体事件与展示 | `ui/MainForm.cs` | 输入和调用应用流程；不堆积分公式和设备协议。 |
| 窗体关联资源 | `ui/MainForm.resx` | 保持 WinForms 配对关系；通用图标和语言文件放 resources。 |
| 检测流程 | `application/DetectionService.cs` 等 | 负责组织调用；不引用具体窗体控件。 |
| 自己编写的采集器 | `source/capture/` 或现有 camera 适配目录 | 自有代码不放 thidparty；第三方 SDK 放 thidparty。 |
| 默认参数 / 现场设置 | `config/` / `data/` | 分开存储，软件升级不能无条件覆盖现场设置。 |
| 自动生成文件 | 生成器声明的专用目录或 `*.g.cs` 等标记文件 | 明确能否重建；不手工修改生成输出，不把布局产物与业务混写。 |

一个 `.csproj` 可以先管理多个职责目录。需要独立复用或测试隔离时再拆为多个类库；通过 ProjectReference 引用，不手工复制 C# 源码到多个项目。新增生成源码时检查编译包含项，避免重复编译。测试目录不得被生产项目递归编译进去。

## 3. C++ 与 C# 的连接方式

```text
C# 界面 → C# 应用流程 → C# interop 封装 → C ABI → C++ 算法
                         ↓
                 相机/文件等适配器
```

相机采集和算法输入通过明确的数据结构连接。原生 include 中声明的结构与 managed/interop 中的映射同步修改；用契约验证核对大小、对齐、调用约定、单位、版本及资源所有权。算法不反向依赖 C# 或控件。

第三方按名称集中管理，例如 `thidparty/opencv/`、`thidparty/hp60c/`，内部按实际需要分为 `include/`、`lib/`、`bin/`；不同版本、平台或架构并存时增加版本和平台子目录。保留许可证、来源和版本说明。

- `thidparty/tools/`：可以合法随工程分发的工具。

| 目录 | 用途 | 管理要求 |
| --- | --- | --- |

# C++ / Python 选型与目录规则

## 1. 默认选择

**算法库优先使用 C++。只有直接涉及 AI 模型，或用户明确指定 Python 时，才采用 Python 实现相应功能。**

“AI 直接相关”指模型训练、微调、模型推理、模型导出以及与这些任务直接关联的数据处理；不等于“这段代码由 AI 编写”，也不包括项目中只要有一个 AI 模块就把所有功能改成 Python。

| 工作内容 | 默认语言 |
| --- | --- |
| 图像增强、传统图像识别、点云滤波、平面拟合、标定、几何计算、容积积分 | C++ 算法库 |
| 原生设备适配、性能关键数据处理 | C++；已有适配接口按工程保留 |
| 模型训练、微调、推理、导出及直接相关处理 | 可使用 Python；已有合适的 C++ 推理方案继续使用 |
| 用户明确要求的 Python 工具或程序 | Python，限定指定范围 |
| C# 界面、TypeScript IDE、现有构建脚本 | 保留各自语言，不因算法优先 C++ 而全部改写 |

不能仅以“Python 写起来快”或“某库使用方便”作为新增 Python 算法模块的理由。新建非 AI 工具也不能默认转用 Python；优先现有工程工具链。已有 Python 不自动全库重写，按后续任务范围逐步处理。

## 2. 混合调用边界

- C++ 核心不依赖 Python 解释器，独立编译、测试和发布。
- 对外共享算法以 C ABI 暴露，Windows 输出 DLL，Linux 输出共享库；只声明实际构建验证的平台。
- C# 通过 P/Invoke、Python 可通过 ctypes 调用同一套 C ABI，不各自复制一份生产算法。
- 确需 Python 专用扩展时，可单独增加 pybind11 等绑定层；绑定依赖只属于该层，不进入核心算法库。
- 接口明确单位、坐标、数组布局、长度、所有权、错误及版本。C++ 异常不跨语言边界。
- Python 中与 AI 输入输出直接相关的前后处理可以就近实现；独立通用几何、滤波、测量算法仍优先复用 C++。
- 不以写临时文件、反复启动 Python 子进程作为默认逐帧算法调用方式。

## 3. 目录规则

在现有独立工程规则上按需增加 Python 部分，不创建空目录：

```text

│  │  └─ pyproject.toml          Python 包和依赖声明
│  ├─ bindings/python/           原生 Python 扩展源码（使用时才创建）
│  ├─ managed/                   C# 应用（已有工程保留）
│  └─ tests/python/              Python 及跨语言测试（按需）
├─ thidparty/                    第三方 SDK、绑定库、离线包及环境说明
```

Python 包目录使用小写下划线。保留用户指定的 `thidparty` 拼写。纯 Python 包装和原生扩展只选择实际需要的方式，不能为目录完整同时制造两套重复接口。

## 4. 环境与交付

- Python 项目声明解释器版本和依赖，记录可复现的版本解析结果；沿用已有包管理方式，不无故同时引入多套管理器。

- C++ / Python 编码格式沿用项目按语言制定的规则。当前容积核心继续保持 C++17，本规则不触发编译器或框架升级。

# AI 可读、可维护代码生成约定

适用：本工作区后续开发及修改。目标是让接手者容易定位功能、理解数据流、修改规则和验证结果。既有工程按当前任务逐模块改善，不自动全库重写。本文件是工程约束，不是新模型、自动分析器或质量认证。

## 1. 开始前明确改什么

先读当前模块、调用入口、项目编译配置和相关测试，再确定：

- 本次具体输入、输出、异常情况和验收行为。
- 哪个文件负责界面，哪个负责流程，哪个负责计算或外部访问。
- 当前可复用实现和必须保持的接口、单位、配置、线程与资源生命周期。

小修改无需长设计文档；跨模块修改用简短文字列出调用链及各模块责任。不能未读旧实现就并行增加一套同名功能。信息不足时明确假设，不偷偷填默认值以制造成功结果。

## 2. 让调用顺序容易读懂

- 入口体现真实业务步骤；复杂细节放入具名函数。一个函数负责一个可描述的任务，计算函数尽量显式接收输入并返回结果。
- 按输入校验、主要流程、结果输出的顺序组织。错误条件可提前返回，避免层层嵌套主流程。
- 提取重复且含义一致的规则；外观相似但业务不同的逻辑不强行合并。
- 不使用布尔参数串表达多个模式，优先枚举或含义明确的配置字段；兼容已有公开接口时在内部转换。
- 不依赖隐式全局变量、上次按钮点击状态或控件文本决定算法结果。确需状态时注明归属、修改位置及生命周期。
- 禁止为追求短代码堆叠三元表达式、复杂链式调用、带副作用的条件或一行多条语句。

函数超过约 60 个有效代码行、文件超过约 500 行、嵌套超过 3 层时，作为人工检查信号：检查是否混合职责。它们不是硬性通过标准；生成布局、数据表、清晰的状态处理和性能关键循环可以保留，并说明理由。不把一个连贯过程切碎成大量无意义转发函数。

## 3. 命名、数据和注释

- 使用业务词汇，避免宽泛的 `ProcessData`、`Helper`、`Manager` 承载无关功能。简短循环索引可以保留 `i`，对外数据必须有明确名称。
- 保持模块已有命名风格；不为了风格统一破坏公开 ABI、序列化字段或历史配置。
- 像素、毫米、立方厘米、比例及百分数在名称或类型中区分，例如 `heightMm`、`volumeCm3`、`loadRatio`、`loadPercent`。
- 配置阈值集中命名，说明来源和有效范围；算法中不散落无解释的常数。
- 公共接口注释说明用途、输入输出、合法范围、单位、坐标、所有权、线程要求、失败语义中与该接口有关的部分。
- 复杂算法注释说明公式、物理假设、选择原因和误差边界。中文注释优先便于当前维护者理解，标识符使用明确英文。
- 注释须随代码更新；不要逐行复述赋值、用大段注释掩饰混乱实现，或用“已完成”注释代替实现。

- 所有具名方法（含私有方法、构造函数、事件及局部函数）须有用途说明；复杂方法体说明关键步骤、约束与原因。各语言格式、例外与检查口径见 [方法与方法体注释](rules/METHOD_COMMENTS.md)。

## 4. 分开职责，控制抽象数量

| 责任 | 应放内容 | 不应放内容 |
| --- | --- | --- |
| 界面与绑定 | 布局、输入、触发操作、展示状态 | 测量公式、相机协议、数据库访问 |
| 应用流程 | 调度、取消、会话、状态转换 | 控件绘制、几何积分细节 |
| 算法与业务 | 分格、积分、规则、结果语义 | 窗口引用、按钮状态、相机打开 |
| 外部适配 | 相机 SDK、文件、网络、资源释放 | 擅自修改业务判定 |

只有实际存在这些职责才拆分对应模块，不创建空层。接口用于隔离外部依赖、替换实现或有价值的测试，不要求每个类都有接口。生成布局和手写事件分开，重新生成不得覆盖业务代码。应用必须独立构建与运行，不依赖 IDE 的私有文件。

## 5. 状态和错误必须说得清

- 区分未执行、无数据、无效、有效零值和有效非零值；测量额外区分实测、估算、未知范围。
- 对外返回可判别的错误或状态，在适当边界记录诊断；不空捕获异常、不把失败替换为成功。
- 日志保留操作、原因及相关帧号/会话，避免逐帧重复无界刷屏。用户界面展示可行动信息，技术细节进入日志。
- 明确谁创建、谁释放、何时取消；禁止 UI 线程同步等待长任务和无界队列。结果关联原输入会话，旧会话不能覆盖新结果。
- C++ 用 RAII 管理资源，异常不穿越 C ABI；C# 用 IDisposable、using 或 finally 释放资源；TypeScript 异步操作明确失败与取消路径。

## 6. 针对现有技术栈的边界

- 容积工程保持 C++17、C# 5 / .NET Framework 4.8；不得为了使用新语法升级运行环境。
- Forge IDE 保持其项目声明的 TypeScript、Electron 等版本与进程边界；不得把其框架要求套用到测量程序。
- C++ / C# 共享结构的大小、布局、单位、缓冲区长度及所有权属于接口契约。
- 算法可读性重构不得改变积分口径、补偿假设、阈值、点云尺度、箱规匹配或缺测处理；需要改变时作为明确的行为修改说明并验证。
- 第三方代码保留来源及许可证，不为了本规则批量格式化；生成产物通过生成器修改。

## 7. 每次修改后的自查与验证

先阅读自己修改后的调用链，再逐项回答：

1. 接手者从入口能否定位关键规则？新名称是否准确？
2. 本次修改是否混入另一项职责、重复实现或不必要抽象？
3. 输入、单位、状态、错误、资源及并发边界是否明确？
4. 方法声明（含私有、事件与局部函数）是否有说明？方法体的关键步骤、假设、并发与失败处理是否有准确注释？
5. 是否保持要求的兼容性，是否有无关格式化或隐藏行为变化？
6. 哪个测试或样本能证明此次行为？这个验证能否在代码出错时失败？

按改动选择实际验证：编译与已有相关检查；算法使用已知真值和边界/回归样本；跨语言改动检查 ABI；流程改动检查取消、失败与会话；模板改动编译生成工程。小文案、注释改动无需新增形式化测试。工具未安装或未运行必须明说。离线通过不代表现场精度通过。

## 8. 可直接复用的任务提示词
